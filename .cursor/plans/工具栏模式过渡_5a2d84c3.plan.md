# 阅读编辑工具栏过渡

## 总体目标

- `编辑 -> 阅读`
- 工具栏顶部固定不变，底部向上收拢，内部按钮同时变淡并缩小。
- 当外框高度收拢到与宽度一致后，工具栏以正方形形态向右移出屏幕。
- `阅读 -> 编辑`
- 以上过程完整倒放。
- 逻辑约束
- `workspaceMode` 仍在点击当帧切换，阅读模式的输入/命令门控不等待动画结束。

## 关键架构决定

- 保持 [MyCanvas_Ver_0/Platform/Shared/Toolbar/CanvasToolbarStateBuilder.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/Toolbar/CanvasToolbarStateBuilder.swift) 只负责 steady state，不把动画语义混入 `workspaceMode` 的业务规则。
- 外框几何继续由 [MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift) / [MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift) 驱动，因为这两处已经是 `toolbarHostView.frame` 和 placement pass 的真源。
- 内部按钮的淡出、缩小、裁切继续由 [MyCanvas_Ver_0/Platform/iOS/Canvas/iOSCanvasToolbarHostView.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/Canvas/iOSCanvasToolbarHostView.swift) / [MyCanvas_Ver_0/Platform/macOS/Canvas/macOSCanvasToolbarHostView.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/Canvas/macOSCanvasToolbarHostView.swift) 负责。
- 过渡期间使用缓存的 `fromFrame` / `collapseFrame` / `offscreenFrame` / `toFrame` 做插值，中间不每帧重解 steady layout，避免 iOS 上 `historyButtonsStackView` 显隐改变 blocker 后导致轨迹抖动。
- 动画期间要抑制 steady render 和 layout re-entry 对 `toolbarHostView.frame` 的覆盖；结束后再统一 reconcile 回稳态布局。

## 分阶段计划

### Phase 0：共享过渡契约与几何规则

- 目标
- 把“逻辑模式切换”和“工具栏展示过渡”从语义上拆开，建立 steady state 与 transition state 的边界。
- 主要落点
- `Platform/Shared/Toolbar/` 下新增共享过渡类型和几何 helper，供双端控制器和 Host 共用。
- 计划内容
- 定义过渡阶段：`visible`、`hidden`、`collapsing`、`expanding`，以及必要的子阶段或分段 progress。
- 定义几何规则：
- 完整 frame -> 顶部固定的正方形 frame
- 正方形 frame -> 右侧离屏 frame
- 反向进入时从离屏正方形 -> 正方形 -> 完整 frame
- 明确 steady state 的真源仍然是 `CanvasToolbarStateBuilder`，transition 只是一层 presentation override。
- 明确 transition 期间控制器持有上一态/目标态的 toolbar snapshot，Host 只消费 presentation，不直接推导业务模式。
- 验收口径
- 共享层可以纯函数地从完整 frame 算出收拢 frame、离屏 frame，以及对应的视觉 progress 映射。
- 共享层不引入对 `CanvasEditorSession`、`UIView`、`NSView` 的耦合。

### Phase 1：Toolbar Host 展示层改造

- 目标
- 让双端 Host 具备“在不切 steady hidden 的前提下完成退场/入场动画”的能力。
- 主要文件
- [MyCanvas_Ver_0/Platform/iOS/Canvas/iOSCanvasToolbarHostView.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/Canvas/iOSCanvasToolbarHostView.swift)
- [MyCanvas_Ver_0/Platform/macOS/Canvas/macOSCanvasToolbarHostView.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/Canvas/macOSCanvasToolbarHostView.swift)
- 计划内容
- 引入单独的内容裁切容器，让 Host 外框缩高时只裁切内容，而不是直接把按钮栈压缩到产生 Auto Layout 冲突。
- 调整当前按钮栈约束模型，使其可以在“Host 变矮”时保持顶部锚定，不因底部强约束而出现约束告警。
- 新增 transition 渲染接口，让 Host 能在 steady state 之外接收：
- 当前展示用的 toolbar items snapshot
- 按钮内容的 alpha / scale
- 是否禁用交互
- 当前是否处于 transition
- 保留现有 steady `render(_ state: CanvasToolbarState)`，但增加“transition active 时不因 `items.isEmpty` 立刻 hidden”的能力。
- completion 后再切回 steady render，保证 `measuredContentSize()` 和 `isHidden` 恢复到最终业务状态。
- 验收口径
- Host 能显示编辑态按钮快照，同时外框缩到正方形时不报约束冲突。
- 退场过程中按钮逐步变淡和缩小；入场过程中反向恢复。
- transition 期间按钮不可点击，steady state 恢复后可点击。

### Phase 2：iOS 控制器动画编排

- 目标
- 在 iOS 上把模式切换改造成“逻辑立即切换，展示延迟退场/入场”的完整时序。
- 主要文件
- [MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift)
- 计划内容
- 在模式切换入口把当前 toolbar state 与当前 frame 作为 `from` 快照缓存下来。
- `编辑 -> 阅读`
- 先缓存完整 toolbar 的 state / frame。
- 再立即切换 `workspaceMode`，让阅读模式的输入/命令门控立刻生效。
- 用缓存快照继续渲染 Host，并驱动第一段“顶部固定的收拢动画”。
- 第一段结束后驱动第二段“正方形向右离屏”。
- completion 后才把 Host 切到 steady hidden。
- `阅读 -> 编辑`
- 先立即切换 `workspaceMode`，得到 steady editing toolbar state。
- 用 steady editing state 解出目标完整 frame。
- 根据目标完整 frame 反推离屏正方形起点。
- 先让 Host 以“离屏正方形 + 缩小淡化按钮”的展示态挂载，再执行滑入和展开。
- completion 后切回 steady visible。
- 把 `renderToolbar()`、`updatePreparedToolbarPlacement()`、`applyToolbarFrame(_:)` 这条链改造成“transition active 时优先尊重 transition frame，而不是每次都覆盖成 steady frame”。
- 验收口径
- iOS 上完整满足两段式动画要求。
- 模式切换后，阅读模式输入门控立即生效；动画只是展示延迟，不影响命令语义。
- 动画过程中即使触发额外 layout，也不会把 `toolbarHostView.frame` 跳回 steady frame。

### Phase 3：macOS 控制器动画编排

- 目标
- 以与 iOS 对称的时序在 macOS 上实现同样的动画与状态收口。
- 主要文件
- [MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift)
- 计划内容
- 复用 Phase 0 的共享几何规则和 Phase 1 的 Host 展示接口。
- 对 `编辑 -> 阅读` / `阅读 -> 编辑` 采用与 iOS 相同的快照、目标 frame 计算和 completion 收口方式。
- 在 macOS 侧加上 transition active 期间的 steady render 抑制和 `applyToolbarFrame(_:)` 保护，避免 `viewDidLayout` / overlay layout 把动画 frame 覆盖掉。
- 根据 macOS 侧视图层级，确保 Host 内部缩放与透明度变化可稳定生效，不依赖隐式行为不确定的默认状态。
- 验收口径
- 双端动画视觉顺序一致。
- 不出现 macOS 特有的 frame 抖动、按钮闪烁或 completion 后残留错误状态。

### Phase 4：布局重入与 chrome 联动收口

- 目标
- 收口 animation 与 chrome layout 链之间的竞争，避免小地图、context menu、history buttons 造成轨迹抖动或过早回流。
- 主要文件
- [MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift)
- [MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift)
- [MyCanvas_Ver_0/Platform/Shared/Toolbar/CanvasToolbarPlacementPass.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/Toolbar/CanvasToolbarPlacementPass.swift)
- 计划内容
- transition 期间冻结外框轨迹所需的关键几何输入，不依赖中途 blocker 变化去重新解算路径。
- completion 后统一触发一次 steady layout reconcile，让 toolbar、miniMap、context menu 回到最终布局。
- 明确 transition 期间其他 chrome 是否需要立即响应模式变化；默认以“不打断 toolbar 轨迹”为优先，必要时允许其他 chrome 在 completion 后再完成最终收口。
- 针对 iOS 侧 `historyButtonsStackView.isHidden = isReadingModeActive` 带来的 blocker 变化，确保它不会让 toolbar 在退场中途改道。
- 验收口径
- 动画中 toolbar 轨迹连续，没有被 chrome 重新布局打断。
- completion 后 overlay layout 回归 steady state，没有遗留错误 blocker。

### Phase 5：验证与回归检查

- 目标
- 把需求和潜在回归项一次性验透。
- 验证场景
- `编辑 -> 阅读`
- `阅读 -> 编辑`
- 普通编辑态
- 文字选中导致 `crop` 不显示的工具栏形态
- 裁剪态导致 `crop` 为激活态的工具栏形态
- iOS 上 history buttons 显示/隐藏切换场景
- macOS 上窗口尺寸变化或 layout 重入场景
- 验收口径
- 顶部始终固定不变。
- 收拢阶段只有底部向上移动。
- 按钮在收拢过程中同步变淡和缩小。
- 高度收成正方形后才开始向右离屏。
- 反向进入编辑模式时完整倒放。
- 动画期间工具栏不可误触发命令。
- 阅读模式门控立即生效，不因动画延迟而泄漏编辑行为。

## 阶段依赖

1. 先完成 Phase 0，明确共享过渡契约和几何规则。
2. 再完成 Phase 1，给双端 Host 准备好 transition 展示能力。
3. Phase 2 和 Phase 3 可以按同一契约分别落地到 iOS、macOS。
4. Phase 4 负责把动画与 chrome layout 的竞争关系收口。
5. 最后用 Phase 5 做完整联调和回归验证。

## 关键时序

1. `编辑 -> 阅读`
2. 缓存当前 toolbar 的 state 和 frame。
3. 立即切换 `workspaceMode`。
4. 用缓存 state 继续显示 toolbar，并执行“收拢到正方形”。
5. 再执行“正方形向右离屏”。
6. completion 后切回 steady hidden，并 reconcile 最终布局。
7. `阅读 -> 编辑`
8. 立即切换 `workspaceMode`。
9. 解出 steady editing toolbar 的目标 state 和目标完整 frame。
10. 从目标 frame 反推离屏正方形起点。
11. 先滑入正方形，再展开到完整 toolbar。
12. completion 后切回 steady visible，并 reconcile 最终布局。

## 最终验收清单

- 双端都完成与需求一致的两段式工具栏动画。
- steady state 业务语义不被动画污染，阅读模式输入/命令门控保持立即切换。
- Host 在缩高过程中没有约束冲突和视觉闪烁。
- 动画不会被 `renderToolbar()`、`applyToolbarFrame(_:)`、`viewDidLayout` 或 blocker 变化打断。
- completion 后 toolbar、miniMap、context menu 都能回到正确的 steady layout。
