# 阅读编辑工具栏过渡

## 总体目标

- `编辑 -> 阅读`
- 工具栏顶部固定不变，底部向上收拢，内部按钮同时变淡并缩小。
- 当外框高度收拢到与宽度一致后，工具栏以正方形形态向右移出屏幕。
- `阅读 -> 编辑`
- 以上过程完整倒放。
- 逻辑约束
- `workspaceMode` 仍在点击当帧切换，阅读模式的输入/命令门控不等待动画结束。

1. 先完成 Phase 0，明确共享过渡契约和几何规则。

## 关键时序

1. `编辑 -> 阅读`
2. 缓存当前 toolbar 的 state 和 frame。
3. 立即切换 `workspaceMode`。
4. 用缓存 state 继续显示 toolbar，并执行“收拢到正方形”。
5. 再执行“正方形向右离屏”。
6. completion 后切回 steady hidden，并 reconcile 最终布局。
7. `阅读 -> 编辑`
8. 立即切换 `workspaceMode`。
9. 解出 steady editing toolbar 的目标 state 和目标完整 frame。
10. 从目标 frame 反推离屏正方形起点。
11. 先滑入正方形，再展开到完整 toolbar。
12. completion 后切回 steady visible，并 reconcile 最终布局。

```swift
// /Users/shaun/Library/Mobile Documents/com~apple~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/Toolbar/CanvasToolbarTransitionState.swift
import CoreGraphics

enum CanvasToolbarTransitionDirection: Sendable {
    case toReading
    case toEditing
}

enum CanvasToolbarTransitionStage: Sendable {
    case steadyVisible
    case collapsing(progress: CGFloat)
    case exiting(progress: CGFloat)
    case hidden
    case entering(progress: CGFloat)
    case expanding(progress: CGFloat)
}

struct CanvasToolbarTransitionSnapshot: Hashable, Sendable {
    var state: CanvasToolbarState
    var frame: CGRect
}

struct CanvasToolbarTransitionConfiguration: Hashable, Sendable {
    var collapseDuration: TimeInterval
    var slideDuration: TimeInterval
    var minimumContentScale: CGFloat
}

struct CanvasToolbarTransitionFrames: Hashable, Sendable {
    var visibleFrame: CGRect
    var collapsedFrame: CGRect
    var offscreenFrame: CGRect
}

struct CanvasToolbarTransitionContext: Hashable, Sendable {
    var direction: CanvasToolbarTransitionDirection
    var visibleSnapshot: CanvasToolbarTransitionSnapshot
    var settledState: CanvasToolbarState
    var frames: CanvasToolbarTransitionFrames
    var configuration: CanvasToolbarTransitionConfiguration
}

struct CanvasToolbarTransitionPresentation: Hashable, Sendable {
    var frame: CGRect
    var itemStates: [CanvasToolbarItemState]
    var showsBackground: Bool
    var contentAlpha: CGFloat
    var contentScale: CGFloat
    var keepsHostVisible: Bool
    var isInteractive: Bool
}

struct CanvasToolbarTransitionRuntime: Hashable, Sendable {
    var context: CanvasToolbarTransitionContext
    var stage: CanvasToolbarTransitionStage
    var currentPresentation: CanvasToolbarTransitionPresentation
    var pendingLayoutReconcile: Bool
}
```

- Host 私有只允许持有视图结构和渲染实现细节：
- `contentClipView`
- `backgroundView`
- `buttonsStackView`
- 平台特定的 transform / layer / alpha 应用逻辑
- 控制器私有只允许持有动画驱动句柄：
- iOS 的 `UIViewPropertyAnimator` 或等价对象
- macOS 的 `NSAnimationContext` / animator 句柄或等价对象
- 不允许在 iOS / macOS 控制器内再各自定义一套本地 `ToolbarTransitionContext` / `ToolbarTransitionPresentation` / `ToolbarTransitionFrames`。
- 不允许在 Host 内部反向推导 `workspaceMode`、`transitionStage` 或 frame 几何。

## 共享数据结构不变量

- `CanvasToolbarTransitionContext.visibleSnapshot`
- 始终表示这次动画使用的“完整可见工具栏”快照。
- `编辑 -> 阅读` 时，它来自切换前的 editing steady toolbar。
- `阅读 -> 编辑` 时，它来自切换后的 editing steady toolbar。
- `CanvasToolbarTransitionContext.settledState`
- 始终表示动画结束后应该落到的 steady toolbar state。
- `CanvasToolbarTransitionFrames.visibleFrame`
- 始终表示完整展开态的屏幕内 frame，是后续所有几何计算的唯一基准。
- `CanvasToolbarTransitionFrames.collapsedFrame`
- 必须满足 `minY == visibleFrame.minY`，只允许底部上升，不允许顶部漂移。
- `CanvasToolbarTransitionFrames.offscreenFrame`
- 必须保持与 `collapsedFrame` 相同的尺寸和 `minY`，只沿 X 方向右移离屏。
- `CanvasToolbarTransitionPresentation.itemStates`
- 始终来自 `context.visibleSnapshot.state.items`，不允许平台侧在动画中自行裁剪 item 列表。
- `CanvasToolbarTransitionPresentation.frame`
- 是动画中屏幕真实显示 frame 的唯一真源。
- controller rebase、新一轮动画起点、`applyToolbarFrame(_:)` guard 都必须读取这个值，而不是回退到 steady frame。
- 收拢后的正方形边长以 `visibleFrame.width` 为准。
- `CanvasToolbarChromeMetrics` 只作为 frame 缺失时的兜底推导，不允许双端分别再推一套边长公式。

## Phase 承接契约

### Phase 0 -> Phase 1

- Phase 0 的交付物必须包括：
- 共享类型命名、字段和不变量冻结。
- `CanvasToolbarTransitionGeometry` 的输入输出冻结。
- `visibleFrame / collapsedFrame / offscreenFrame` 语义冻结。
- 在 Phase 1 开始前，不允许 Host 自行发明临时 `presentation` 结构。
- 如果 Phase 1 发现字段缺口，必须回到共享 contract 统一补齐，不能先在 iOS Host 本地加字段。

### Phase 1 -> Phase 2 / Phase 3

- Phase 1 的交付物必须包括：
- iOS / macOS Host 都具备同名 transition 接口。
- Host 已经能消费 `CanvasToolbarTransitionPresentation` 完成裁切、透明度、缩放和交互禁用。
- Host 已经从“按钮栈强约束直连 Host 外框”的结构升级为“可裁切收拢”的结构。
- 在 Phase 2 / Phase 3 中，控制器只能通过 Host 公开接口驱动动画。
- 不允许控制器直接操作 Host 内部 `buttonsStackView`、`backgroundView` 或自建一套 platform-specific presentation 应用逻辑。

### Phase 2 -> Phase 3

- Phase 2 在 iOS 上验证通过后，必须把以下命名和状态模型视为冻结：
- `toolbarTransitionRuntime`
- `beginToolbarModeTransition(to:)`
- `prepareToolbarTransitionContext(direction:)`
- `finishToolbarModeTransition(...)`
- `cancelAndRebaseToolbarTransitionIfNeeded(targetMode:)`
- Phase 3 必须复用相同的共享数据结构和阶段语义，不允许为了 macOS 单独改出另一套 stage 命名或 frame 语义。
- 如果 macOS 落地时发现共享字段不足，必须回补共享 contract，并同步校正 iOS，不允许只在 macOS 控制器私加字段。

### Phase 3 -> Phase 4

- Phase 3 完成后，双端都必须已经能跑完整的基础出入场动画。
- Phase 4 只负责 layout stabilization、reconcile 和 chrome 联动。
- Phase 4 不允许再新增共享 transition 字段，除非证明当前 contract 无法表达双端共同需求，并同步回补到 Phase 0 契约层。

### Phase 4 -> Phase 5

- Phase 4 的交付物必须是“动画轨迹不会被 steady layout 打断”的稳定运行态。
- Phase 5 只做验收、回归和参数微调。
- Phase 5 不应再改变共享数据结构和阶段语义，否则说明前序 phase 的契约定义仍不完整。

## 控制器建议新增入口

- `beginToolbarModeTransition(to:)`
- 模式按钮点击后的统一入口，负责决定 `toReading` / `toEditing`。
- `prepareToolbarTransitionContext(direction:)`
- 抓取 `fromState`、`toState`、`fromFrame`、`toFrame`，并计算 `collapsedFrame` / `offscreenFrame`。
- `runToolbarCollapsePhase(...)`
- 第一段动画，只负责顶部固定、底部收拢、按钮淡出缩小。
- `runToolbarSlidePhase(...)`
- 第二段动画，只负责正方形离屏或回屏。
- `finishToolbarModeTransition(...)`
- completion 收口，恢复 steady render，并执行 overlay layout reconcile。
- `cancelAndRebaseToolbarTransitionIfNeeded(targetMode:)`
- 如果用户在动画中再次切换模式，以当前 presentation 为新的起点重新编排，而不是简单丢弃。

## Host 结构改造建议

- 保留现有 `backgroundView` 和 `buttonsStackView`，但中间增加一层内容裁切容器，例如 `contentClipView`。
- `backgroundView` 继续铺满 Host 外框。
- `contentClipView` 锚定 Host 顶部、左右对齐、底部小于等于 Host 底部。
- `buttonsStackView` 顶部锚定 `contentClipView`，底部不要再用强约束钉死到 Host。
- 这样 Host 在“底部向上升”时，真正变化的是 Host 外框和裁切区域，而不是强行压缩按钮本身的 Auto Layout 尺寸。
- 按钮缩小建议走 stack 容器统一 `transform` / `layer` 缩放，而不是逐个重算按钮约束。

## 动画默认参数

- 第一段 `collapse / expand`
- 建议默认 `0.18s`，使用 easeInOut。
- 第二段 `slide out / slide in`
- 建议默认 `0.14s`，使用 easeInOut。
- 按钮 `alpha`
- `1.0 -> 0.0` 与第一段同步完成。
- 按钮 `scale`
- `1.0 -> 0.78` 与第一段同步完成。
- 默认先求“结构正确、轨迹正确”，时长和曲线在功能落地后再调。

## 中断与重入策略

- 如果用户在动画尚未结束时再次点击模式按钮：
- 不等待旧动画完成。
- 立刻停止当前动画，读取当前 presentation frame 和视觉 progress，重建新的 transition context。
- 新动画从“当前屏幕上真实看到的状态”继续，而不是从旧 steady frame 重新开始。
- 如果动画期间触发 `viewDidLayout`、safe area 变化或窗口尺寸变化：
- 不立即改写当前轨迹。
- 仅设置 `toolbarTransitionRuntime.pendingLayoutReconcile = true`。
- completion 后重新走一次 steady `updatePreparedToolbarPlacement()` 和 overlay layout。
- 如果动画开始时拿不到有效 toolbar frame：
- `编辑 -> 阅读` 直接退化为 steady hidden。
- `阅读 -> 编辑` 直接退化为 steady visible。
- 退化路径要显式记录到计划验收中，避免出现半初始化状态。

## Phase 内部拆分

### Phase 0 内部拆分

1. 定义共享过渡类型。
2. 写出收拢正方形和离屏正方形的纯函数几何规则。
3. 明确 progress 到 `frame / alpha / scale / keepsHostVisible` 的映射。
4. 确认收拢正方形边长直接复用 `CanvasToolbarChromeMetrics` 推导，不引入重复常量。

### Phase 1 内部拆分

1. 先重构 Host 内部层级和约束，确保“缩高到正方形”不报约束冲突。
2. 再加 transition presentation 渲染入口。
3. 最后再接按钮淡出缩小和交互禁用。

### Phase 2 / Phase 3 内部拆分

1. 把模式切换按钮入口改造成统一 transition 入口。
2. 把 steady render 与 transition render 的优先级梳理清楚。
3. 再接双段动画。
4. 最后处理 completion 和中断重入。

### Phase 4 内部拆分

1. 收口 `renderToolbar()` 对 transition 的覆盖。
2. 收口 `applyToolbarFrame(_:)` 对 transition frame 的覆盖。
3. 收口 `viewDidLayout` / overlay layout 对动画轨迹的打断。
4. completion 后只做一次最终 reconcile。

## 最终验收清单

- 双端都完成与需求一致的两段式工具栏动画。
- steady state 业务语义不被动画污染，阅读模式输入/命令门控保持立即切换。
- Host 在缩高过程中没有约束冲突和视觉闪烁。
- 动画不会被 `renderToolbar()`、`applyToolbarFrame(_:)`、`viewDidLayout` 或 blocker 变化打断。
- completion 后 toolbar、miniMap、context menu 都能回到正确的 steady layout。
