# 菜单覆盖 Chrome 策略计划

## 目标

- 让上下文菜单可以覆盖悬浮按钮和 `minimap`。
- 继续保留 `safeBounds`、`edgeInset` 这类硬边界约束，不让菜单跑出可用画面。
- 保持 `iOS/macOS` 对称实现，不在 controller 里写“返回空数组”这类平台补丁。

## 现状锚点

- [CanvasContextMenuState.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/ContextMenu/CanvasContextMenuState.swift)：`CanvasContextMenuLayoutSolver.resolveMenuFrame(...)` 当前把 `occupiedRects` 统一扩张成 blocker，并优先寻找 `overlap = 0` 的候选位置。
- [CanvasContextMenuHostView.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/ContextMenu/CanvasContextMenuHostView.swift)：host 只是把 `safeBounds`、`occupiedRects`、`layoutAnchorPoint` 透传给 solver，本身不决定是否避让 chrome。
- [iOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift) 与 [macOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift)：controller 当前会继续测量 `controlsStackView` 和可见 `miniMapMountView`，并把它们转成 `contextMenuHostView` 坐标系后作为 `contextMenuOccupiedRects()` 传下去。

## 实施步骤

- 在 [CanvasContextMenuState.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/ContextMenu/CanvasContextMenuState.swift) 新增共享布局策略枚举，例如 `CanvasContextMenuOcclusionPolicy`，至少包含：
  - `avoidOverlayChrome`
  - `allowChromeOverlap`
- 把该策略挂到 `CanvasContextMenuLayoutConfiguration`，与现有 `edgeInset`、`anchorSpacing`、`chromeClearance` 同层管理。这样“菜单是否避让 chrome”仍然是纯布局配置，而不是上下文状态。
- 修改 `CanvasContextMenuLayoutSolver.resolveMenuFrame(...)`：
  - 继续始终使用 `safeBounds` + `edgeInset` 作为硬约束。
  - 仅在 `avoidOverlayChrome` 下把 `occupiedRects` 扩张为 blocker。
  - 在 `allowChromeOverlap` 下忽略 `occupiedRects` 对菜单选位的影响，但不影响既有 `safeBounds` clamp。
- 在 [CanvasContextMenuHostView.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/Shared/ContextMenu/CanvasContextMenuHostView.swift) 为内部 `layoutConfiguration` 设定明确策略来源：
  - 如果这个需求是新的全局默认行为，直接把默认配置设为 `allowChromeOverlap`。
  - 如果你希望后续仍能切换，保留 host 持有可注入的 `layoutConfiguration`，但不把策略暴露成每次 `apply/updateLayout` 的调用参数。
- 保持 [iOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift) 与 [macOSViewController.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Platform/macOS/macOSViewController.swift) 的职责不变：
  - 继续生成 `contextMenuSafeBounds()`。
  - 继续生成并转换 `contextMenuOccupiedRects()`，供共享层在不同策略下使用。
  - 不在 controller 里新增“菜单允许覆盖 chrome”判断。
- 不修改 [CanvasContextMenuContext.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Canvas/Core/CanvasContextMenuContext.swift) 和 [CanvasContextResolver.swift](/Users/shaun/Library/Mobile Documents/com~~apple~~CloudDocs/Develop/MyCanvas_Ver_0/MyCanvas_Ver_0/Canvas/Core/CanvasContextResolver.swift)，因为这次不是命中语义问题，而是展示布局策略问题。

## 验证

- `iOS`：长按时菜单可以覆盖右下角悬浮按钮区和左下角 `minimap`，但仍留在 `safeBounds` 内。
- `macOS`：右键菜单可覆盖 chrome，同时保持现有 top-most 宿主与 flipped 坐标链路不回退。
- 交互回归：菜单覆盖在按钮或 `minimap` 上方时，点击应优先命中菜单，不应穿透到底层 chrome。
- 构建回归：`generic/platform=iOS`、`generic/platform=macOS`。
