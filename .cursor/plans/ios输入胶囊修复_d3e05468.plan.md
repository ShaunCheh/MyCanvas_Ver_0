# iOS 输入胶囊根因修复计划

## 根因锚点

当前问题集中在 [MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorHostView.swift](MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorHostView.swift) 的 `iOS` 分支：`applySnapshot(_:animated:)` 在同一个 `UIView.animate` 事务里同时做了两件不同层级的事情。

- 对新胶囊做 `alpha + transform` 入场动画
- 调用 `applyLayout()` / `layoutIfNeeded()`，把 `containerView` 从默认左上角 `0x0` 约束状态插值到底部最终位置

这会让 UIKit 实际动画的是整个宿主容器，而不是“已经位于底部的新胶囊”，因此首个可见轨迹会表现为“从左上角飞到底部”。

```swift
// 文件路径: MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorHostView.swift
// 函数名/符号名: applySnapshot(_:animated:)
// 功能说明: 当前 iOS 分支在同一动画事务里同时推进 item 入场和宿主布局，导致 containerView 从默认左上角状态插值到底部。
let applyVisualState = {
    for item in snapshot.items {
        guard let view = self.itemViewsByID[item.id] else {
            continue
        }
        view.alpha = item.opacity
        view.transform = .identity
    }
    self.applyLayout()
    self.layoutIfNeeded()
}

UIView.animate(withDuration: Layout.animationDuration) {
    applyVisualState()
}
```

从架构边界上看，[MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift](MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift) 只是把 `CanvasChromeLayoutContext` 和 `indicatorEvent` 分别喂给宿主；真正的同步责任应该留在 host 内部，而不是把修复扩散到 controller。

```swift
// 文件路径: MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift
// 函数名/符号名: updateChromeOverlayLayout() / recordCapturedInputIndicator(_:)
// 功能说明: controller 侧分别负责布局上下文更新与事件记录，宿主自身应处理“何时落位、何时动画”的时序问题。
let contextMenuLayoutContext = performOverlayLayoutPass()
updateInputIndicatorLayout(using: contextMenuLayoutContext)

inputIndicatorHostView.record(event: indicatorEvent)
```

## 实施步骤

1. 在 [MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorHostView.swift](MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorHostView.swift) 的 `iOS` 分支里拆分 `applySnapshot(_:animated:)` 的职责：

- 先重建 arranged subviews 和 `currentSnapshot`
- 再无动画求解并提交宿主最终布局
- 最后只对 item 做可见性与位移动画

1. 为 iOS host 增加“布局先行”的稳定落位流程：

- 在开始任何 item 动画前，先调用 `applyLayout()` 并配合 `UIView.performWithoutAnimation { layoutIfNeeded() }` 把 `containerView` 固定到底部目标位置
- 如果当前没有 `currentLayoutContext`，则先缓存 snapshot、保持 host 隐藏，不在未知位置提前显示胶囊；等后续 `updateLayout(layoutContext:)` 到来后再按最终位置渲染

1. 用 item 级 FLIP 动画保留原有交互语义，而不是依赖宿主位移“顺带”带出动画：

- 在重建 `stackView` 之前记录现有 item 的旧 frame
- 宿主完成无动画落位后，计算既有 item 的 `deltaY`
- 让新插入 item 继续使用 `Layout.insertionTranslationY`
- 让已有 item 先带着 `deltaY` 的 transform 呈现，再统一动画回 `.identity`
- 这样可以保留“新胶囊从底部冒出、旧胶囊被顶上去”的效果，同时彻底切断左上角飞入轨迹

1. 收口刷新与衰减场景的动画边界：

- `refreshTimer` 驱动的淡出更新只允许影响 item 的 `alpha` 与必要的 item transform
- 不再让 timer tick 触发宿主位置动画
- `snapshot.isEmpty` 时仍沿用现有隐藏语义，但避免产生额外的宿主位移动画

1. 仅当实现中发现“首个事件先于首次 layout context 到达”仍需要 controller 辅助时，再考虑在 [MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift](MyCanvas_Ver_0/Platform/iOS/iOSViewController.swift) 增加一个非常局部的同步钩子；默认不走这条路，先保持修复收敛在 host 内。

## 验证策略

- iPhone 模拟器/真机：首次 `Tap`、连续 `Tap`、`Command + C / V`、滚动/缩放后触发输入胶囊，确认胶囊不再从左上角飞入，而是直接在底部出现并播放本地入场动画。
- 堆栈行为：连续多次触发输入时，确认新胶囊在底部插入，旧胶囊向上推移并按既有 queue 规则渐隐。
- 布局避让：确认输入胶囊仍遵守 [MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorLayoutSolver.swift](MyCanvas_Ver_0/Platform/Shared/InputIndicator/CanvasInputIndicatorLayoutSolver.swift) 的底部避让语义，不与 toolbar / miniMap 重叠。
- 模式切换：在普通画布态与文本编辑态之间切换后再次触发输入，确认宿主不会因为 layout context 更新时机不同而出现首帧漂移。
- 测试策略：这次优先以手工回归为主，不新增高噪音 UIKit 动画快照测试；若实现中抽出纯函数级 helper，再补纯逻辑测试。
